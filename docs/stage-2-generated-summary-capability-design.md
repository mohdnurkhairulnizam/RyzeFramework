# Stage 2 generated-summary capability design

**Status:** bounded backend/provenance implementation present and locally tested; live skill/intent benchmark remains open

## Purpose

Define the narrow capability behind a request such as “make a short Markdown summary of README.md and send the summary as a file.” This is separate from the existing-file resend path and must not turn Ryze into a general file-writing or shell-execution agent.

## Allowed operation

The owner may explicitly request a generated Markdown summary from an owner-authorized source file that is already available through Ryze's bounded file pathway. The operation creates a new server-generated artifact with a distinct storage key and source binding. It never overwrites the source file and never accepts an arbitrary destination path.

The initial scope is limited to Markdown output, UTF-8 text, a bounded source size of 64 KiB, a bounded generated size of 64 KiB, and the existing owner-scoped file store. The source must belong to the requesting owner and must remain within its retention window.

## Required authorization and review

The request must be an explicit owner-scoped action. The server, not model text, decides the source file, output type, size limits, storage key, and destination chat. The generated artifact records the source file ID, source content hash, requesting owner, task ID, creation time, and generator/provider label. The source content is untrusted document data and is sent to the configured model provider only after the owner is told that analysis uses that provider.

The generated artifact is queued for delivery only to the exact originating authorized private chat, using the existing source-bound file-send path. No group, broadcast, proactive, cross-chat, arbitrary path, shell, or general tool destination is permitted. If the source or destination binding cannot be proven, the operation fails closed.

## Confirmation, rollback, and retention

Before delivery, Ryze should present the proposed source, output type, and bounded size to the owner-facing flow. A generated artifact must be distinguishable from the source attachment. Provider failure, malformed output, size overflow, source deletion/expiry, or acknowledgement mismatch leaves the source unchanged and prevents delivery. The generated artifact follows the same 30-day file retention and owner deletion controls as other generated files.

A retry must use a durable idempotency key derived from the owner, source file ID, source hash, task ID, and requested operation. It must not create duplicate deliveries after an acknowledged send or uncertain send.

## Acceptance tests

1. A synthetic owner request produces a distinct Markdown artifact with source binding and a different storage key.
2. The source file remains unchanged and retrievable.
3. The generated artifact is limited to Markdown/UTF-8 and the configured size cap.
4. An unauthorized owner, expired source, arbitrary path, cross-chat destination, or shell-like instruction is rejected server-side.
5. Provider failure and malformed output do not create a deliverable artifact.
6. Duplicate retry does not create a second delivery.
7. Retention expiry and owner deletion remove generated bytes and metadata without deleting unrelated files.

The bounded backend/provenance implementation is present and covered by repository tests. This design still does not authorize broad implementation in the live skill/intent layer. A separate reviewed intent change and target-Windows owner-facing benchmark are required before claiming natural-language summary creation is complete.
